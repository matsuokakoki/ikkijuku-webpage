# 構成と運用

## 選定

- Astro / TypeScript: 案内・料金・実績中心のサイトに合わせ、公開済みコンテンツをHTMLに含める。閲覧時のSDKやDB待ちをなくす。
- microCMS Hobby: 日本語の編集画面と公式MCP。旧管理画面の入力項目を再現する。独自の認証・CMSを作らない。
- Cloudflare Pages Free: 静的ファイルをCDNから配信する。ドメイン以外は有料プランを使わない。
- GitHub: コード、編集モデル、検証を管理する。

## 先生が編集するデータ

| API          | 対象                                                                           | 元データ                                |
| ------------ | ------------------------------------------------------------------------------ | --------------------------------------- |
| news         | お知らせ本文・日付                                                             | pages/home/news                         |
| site（単一） | 募集状況、授業時間、料金・受講例、実績の見出しと一覧                           | pages/home/acception と pages/home/info |
| achievements | 年度、高校生・浪人生・中学生の人数、大学・高校・中学の学校名、学部・人数・備考 | achievements/{year}                     |
| calendar     | 月、休講日、公開・下書き                                                       | holidays と templates/weekly/visibility |

旧お知らせには独立したタイトルがなかったため、移行時は本文をタイトルとして設定しています。日付はmicroCMSの公開日時から日本時間で表示します。過去の公開日は移行で維持します。年度別の人数が未入力だった学校は人数を表示しません。

## 出欠システムとの境界

出欠システム自体と生徒データは変更しません。新ホームページのカレンダーは移行時点の公開データです。移行後はCMSのカレンダーを正とし、旧出欠システムの休講日を自動同期する仕組みはまだありません。先生が両方に同じ休講日を使う場合は二重入力になるため、正式切り替え前に運用を確認します。非公開の未来月は公開データへ含めません。

## 公開

CMSの公開済みデータを取得 → スキーマ検証 → HTML生成 → 内部リンク・秘密情報チェック → Pagesに配信。

ビルド失敗時は公開済みHTMLを置き換えません。下書きは公開ビルドに含めません。公開の自動反映にはGit連携とCMSのWebhook設定が必要です。初期公開はDirect Uploadで行っています。

## 費用

アプリの実行・CMS・静的配信は無料プランを使います。独自ドメイン代のみ別途。microCMS Hobbyは3人・5API・20GB/月、Pages FreeのGitビルドは500回/月です（契約時に公式条件を再確認）。無料枠を超えても自動で有料へ変更しません。CMSの停止時も既存HTMLは引き続き配信されますが、内容更新は止まります。

## 安全対策

CMSキーはビルド環境だけで扱い、公開ファイルへ含めません。本文は許可したHTMLだけを出力します。外部スクリプト・フォントを読み込まず、CSP、クリックジャッキング対策、MIME保護などを設定します。CMSとGitHub、Cloudflareは個別アカウントと2要素認証を使ってください。Hobbyでは細かな編集権限分離を使えない制約があります。

## バックアップ・復元

`src/data/snapshot.json`は初回移行時の公開コンテンツです。最新CMSデータのバックアップとは異なります。`node --env-file=.env scripts/backup-content.mjs /安全な保存先/backup.json`で公開中の4APIをJSONに保存できます。キーは環境変数に設定し、バックアップに含めません。下書きや非公開コンテンツはこの手順の対象外です。

復元は既存APIのスキーマを確認し、バックアップから対象レコードを復元、ビルド検証、Pagesへ再配信の順で行います。初回移行のレコードIDは維持し、お知らせのスターター記事のみ実データに置き換えています。誤公開の緊急復旧にはPagesの過去デプロイへのロールバックも利用できます。
